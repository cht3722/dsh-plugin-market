HOW IT WORKS

从需求到结论，每一步都能回查。

01 / 准备

冻结来源

读取目标工程、Spec 和可选的 Android 行为基线，生成本次运行的来源快照。之后都从这份快照回查原文。

“Spec 在 /absolute/spec。”
02 / 输入

统一验收输入

把需求整理成带追溯 ID 的验收项，写清预期、前置条件和来源引用；判断不了的预期标为待复核，不替调用者补答案。

“缺少依据的要求保留未验证。”
03 / 计划

候选计划与统一审查

各验证方式分别提出候选计划，再统一审查：每一项都要有接受或拒绝的理由，没覆盖到的要求保留为缺口。

“只做到正式计划接受为止。”
04 / 执行

执行与汇总

按正式计划执行，每次执行独立留档。执行状态（通过、失败、受阻）和验收结论（满足、违反、未验证）分开记录，汇总到结果文件。

“返回结果文件与证据位置。”

VERIFICATION METHODS

按要求选择合适的验证方式。

UT

Harmony 单元测试

为业务逻辑编写 Hypium 单元测试；提交计划前先核对注册的用例并编译测试 HAP，再在设备或模拟器上执行。

UI

Harmony 界面测试

按页面编写 Python Hypium 脚本，经门禁检查后在受控沙箱中执行，由宿主独立采集和复核界面证据。

STATIC

静态依赖检查

对 TS/JS 工程按认可的来源规则检查静态 import，扫描结果可复算，不需要设备。

REPAIR

按授权修复

调用者明确授权后，UT/UI 修复插件按失败包修改生产代码并复测；修复插件不改测试，判断测试本身有问题时提出申诉。

IN YOUR WORKFLOW

装好插件，在会话里发起验证。

插件随包提供 dt-verify Skill、验证运行资源和 4 个子 Agent 角色；模型、会话和工具权限沿用 DSH 本身的设置。

运行时
DSH 0.2.1-rc.2（包声明兼容 ^0.2.1-rc.2）；Node 22.22 以上的 22.x、24.x 或 26 及以上；pnpm。
Harmony 环境
UT/UI 需要 HarmonyOS SDK、hvigor、ohpm、hdc，以及设备或模拟器。
UI 额外要求
macOS（sandbox-exec）、Python 3.11 及以上、Hypium 6.1.0.210；用 DT_VERIFY_PYTHON 指定解释器。
子 Agent
编写与修复可按页面或功能组并行，由随包角色执行；宿主不能委派时按顺序处理。

四个步骤开始使用

  1. 安装插件

    在「插件 → 发现」中找到“DT 验证组件”并安装；也可以执行 dsh plugin --profile web add --save-exact dt-verify-deepseek@0.1.0-dev.19。本机 npm 使用镜像时，需等镜像同步，或把 registry 指向 registry.npmjs.org。安装后重启 DSH。

  2. 配置模型与工作区

    在「设置 → 模型」中配置模型凭据，选择目标工程作为工作区，用标准 preset 新建会话。

  3. 发起验证

    例如：“使用 dt-verify 验证当前工程，Spec 在 /absolute/spec，按 Skill 完成计划、审查、执行和汇总。”迁移场景再给出 Android 工程路径；需要修复时写明授权范围。

  4. 查看结果

    打开汇总文件，按验收项查看执行状态、验收结论和原始证据位置。

理解结果的范围

未验证就是未验证。缺少环境、设备或依据的要求保持受阻或未验证，不会缩小验收范围，也不会被其他项的通过补齐。

环境要求不随宿主改变。UT/UI 结论需要真实的 SDK 与设备执行证据；UI 执行目前只支持 macOS。Harmony 构建会写入用户目录下的缓存，在 DSH 默认的工作区写入权限下可能需要逐次授权。

预览版。当前为开发候选版本，接口与行为可能随后续版本调整。
